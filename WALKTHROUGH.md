# WALKTHROUGH — как эта система устроена (плоским языком)

Документ для того, чтобы **понимать каждый кусок** проекта: и для защиты на
интервью, и как основа для поста. Читается сверху вниз, без предварительных знаний.

---

## 1. Что это вообще и зачем

**Проблема, которую решаем.** Бизнес хочет ответы на вопросы по данным
(«сколько депозитов по странам?»), но не умеет писать SQL и не хочет ждать
аналитика. Идея: пусть спрашивает словами, а система сама достаёт ответ из базы.

**Наивное решение (плохое):** дать LLM схему базы и попросить «напиши SQL».
Так делают многие — и получают галлюцинации: модель выдумывает несуществующие
колонки, путает джойны, считает не на том уровне детализации. Ответы недостоверны.

**Наше решение (правильное):** LLM **не пишет SQL**. Между пользователем и базой
стоит **семантический слой** — словарь проверенных метрик. LLM только *выбирает*
из этого словаря (какую метрику, по чему разрезать, какие фильтры), а сам SQL
собирает детерминированный код. Модель ошибается только в выборе из готового,
а не изобретает запрос с нуля. Пространство ошибок схлопывается в разы.

> Это ровно та парадигма, которую строят в современных AI-BI: semantic layer как
> «источник знаний», LLM как «переводчик вопроса», движок как «сборщик SQL».

## 2. Путь одного вопроса (главная схема — выучи её)

```
1. Пользователь:   "топ-5 стран по обороту"
        │
2. LLM (llm.py):   смотрит в каталог метрик и возвращает НЕ SQL, а JSON-план:
        │          {"metric": "trading_volume", "group_by": ["country"],
        │           "order": "desc", "limit": 5}
        │
3. Валидация       (semantic.py): а есть ли такая метрика? можно ли резать по
   (semantic.py):  country? — проверка по allow-list, чтобы план был легальным
        │
4. Компиляция      (semantic.py): из плана собирается настоящий SQL —
   в SQL:          с нужными джойнами, встроенными фильтрами, группировкой
        │
5. Guardrails      (guardrails.py): только SELECT? нет запрещённых операций?
        │          не слишком тяжёлый (dry-run EXPLAIN)? ставим LIMIT
        │
6. База (DuckDB):  выполняем безопасный SQL, получаем таблицу
        │
7. Ответ (app.py): показываем "как я понял вопрос" + SQL + таблицу + график
```

И сбоку, независимо: **eval.py** — прогоняет список тестовых вопросов и меряет,
насколько точно система их понимает.

### Два уровня ответа (важно — это осознанный компромисс)

У governed semantic layer есть обратная сторона: он покрывает **только
сертифицированные метрики**. На вопрос «а сколько у нас стран» он ответить не
может — такой метрики нет, хотя `SELECT COUNT(DISTINCT country)` тривиален.
Это цена безопасности: покрытие «длинного хвоста» в обмен на отсутствие
галлюцинаций.

Решение — **два уровня** (ровно как в промышленной агентной архитектуре:
«semantic layer как главный путь + ограниченный read-only SQL как запасной»):

```
Вопрос
  │
  ├─► УРОВЕНЬ 1: semantic layer (governed)         ← основной путь
  │     LLM выбирает сертифицированную метрику.
  │     Есть метрика? → компиляция SQL → guardrails → ответ.
  │
  └─► УРОВЕНЬ 2: governed SQL-fallback              ← если метрики нет
        LLM пишет ОДИН read-only SELECT →
        ТЕ ЖЕ guardrails (SELECT-only, allow-list, LIMIT, dry-run) →
        ответ ПОМЕЧЕН как "вне сертифицированных метрик, ad-hoc".
```

Ключевое: **L2 не обходит защиту** — сгенерированный SQL проходит через тот же
`guardrails.py`. И ответ явно помечается «⚠️ ad-hoc, перепроверьте» — прозрачность:
пользователь видит разницу между governed-метрикой и разовым запросом.
Если настоящей LLM нет (fallback-провайдер) — L2 недоступен, и система честно
отказывает (см. `reject_message`), подсказывая, что она умеет.

Почему это правильно на защите: ты **сам поднимаешь** ограничение своего же
подхода и показываешь инженерный ответ на него — это сильнее, чем делать вид,
что покрыт весь мир.

## 3. Файлы по порядку

### `generate_data.py` — данные
Создаёт синтетическую базу брокера в файле `broker.duckdb`. Три таблицы:
- **clients** — трейдеры (страна, тип счёта, канал привлечения, демо/реальный);
- **deposits** — их депозиты (сумма, дата, статус: confirmed/pending/failed);
- **trades** — сделки (инструмент, оборот, прибыль/убыток).

Логика реалистичная: депозиты только у реальных счетов, сделки только у тех,
кто внёс подтверждённый депозит (воронка «депозит → торговля»). Данные случайные,
но с фиксированным seed=42 — чтобы результаты воспроизводились.

> Почему DuckDB: встроенная база, ноль установки, колоночная (быстрая для аналитики).
> В проде заменяется на ClickHouse/Trino — остальной код не меняется.

### `semantic_layer.yaml` — СЕРДЦЕ проекта
Это «словарь» в текстовом формате. Две главные части:

**Измерения (dimensions)** — по чему МОЖНО резать метрики:
```yaml
country:
  sql: clients.country
  synonyms: [страна, гео, регион, geo]   # чтобы разные слова вели к одному полю
```

**Метрики (metrics)** — каждая это *контракт*:
```yaml
total_deposits:
  label: "Total Deposits, $"
  description: "Сумма подтверждённых депозитов. Только реальные счета, не демо."
  expression: "SUM(deposits.amount_usd)"          # как считать
  filters_builtin: "status='confirmed' AND is_demo=FALSE"  # ВСЕГДА применяется
  allowed_dimensions: [country, account_type, ...]  # по чему можно резать
  synonyms: [депозиты, пополнения, внесения]        # как это называют люди
  owner: finance_analytics                          # кто отвечает
```

Ключевые идеи здесь:
- **`filters_builtin`** — зашитый фильтр. «Депозит» ВСЕГДА означает
  «подтверждённый, не демо» — не важно, кто спрашивает. Это убирает ситуацию
  «у трёх команд три разных выручки» (single source of truth).
- **`synonyms`** — чтобы «пополнения», «внесения», «GMV» вели к одной метрике.
- **`allowed_dimensions`** — метрику `total_deposits` нельзя резать по `symbol`
  (депозиты не связаны с инструментом). Слой это запрещает.
- **`examples`** (few-shot внизу файла) — пары «вопрос → выбор». Это **главный
  рычаг точности**: LLM учится на примерах, а не на длинных правилах.

### `semantic.py` — движок семантики
Загружает YAML и делает три вещи:
1. **`catalog_for_llm()`** — превращает словарь в текст для промпта LLM
   («вот метрики, вот их синонимы, вот по чему можно резать»).
2. **`validate(plan)`** — проверяет план от LLM: метрика существует? разрез
   разрешён? Если нет — ошибка ещё до SQL.
3. **`compile_sql(plan)`** — собирает настоящий SQL из плана. Здесь зашита
   физическая модель (как таблицы джойнятся) — LLM про джойны вообще не знает.

Отдельно `explain(plan)` — человекочитаемое «Я понял вопрос так: метрика
Total Deposits, разрез по country» (это показывается пользователю — прозрачность).

### `llm.py` — слой LLM (провайдер-агностичный)
Отвечает за шаг «вопрос → JSON-план». Поддерживает четырёх «поставщиков»:
- **Anthropic (Claude)**, **OpenAI**, **Ollama** (локально) — настоящие LLM;
- **Fallback** — без всякой LLM, матчит вопрос по синонимам из словаря.
  Нужен, чтобы проект **запускался даже без API-ключа** (у любого проверяющего).

Почему несколько провайдеров: **нет vendor lock**. Меняешь провайдера одной
переменной в `.env`. Та же идея, что и с semantic layer — знания отделены от движка.

Важное: LLM просят вернуть **структурированный JSON** (structured output), а не
текст. Модель физически не может вернуть кривой формат — это первый guardrail.

### `guardrails.py` — защита
Проверки перед выполнением SQL, слоями:
1. **SELECT-only** — запрещаем INSERT/UPDATE/DELETE/DROP и т.п. (защита от порчи данных);
2. **Allow-list таблиц** — обращаться можно только к clients/deposits/trades;
3. **LIMIT** — принудительно, чтобы не вытащить пол-базы в интерфейс;
4. **dry-run (EXPLAIN)** — оцениваем «тяжесть» запроса, **не выполняя** его;
   если слишком тяжёлый — блокируем.
Плюс сама база открыта **read-only** — физически нельзя ничего изменить.

### `pipeline.py` — оркестратор
Связывает всё воедино в класс `Chatbot`. Метод `ask(question)` проходит все шаги
из схемы (раздел 2) и возвращает объект `Answer` (успех/ошибка, объяснение, SQL,
данные). Можно запускать из терминала: `python pipeline.py "вопрос"`.

### `eval.py` — измерение качества (твой козырь)
«Unit-тесты для AI». Список из ~10 вопросов с эталонными ответами (какую метрику
и разрезы система ДОЛЖНА выбрать) + вопросы, которые она должна **отклонить**
(«какая погода»). Считает три числа:
- **plan_accuracy** — доля вопросов, где выбор совпал с эталоном;
- **exec_success** — доля, где SQL успешно выполнился;
- **reject_correct** — доля правильно отклонённых «не-вопросов».

Зачем: меняешь промпт или модель — прогоняешь eval, видишь, не сломалось ли
(регрессии). Это превращает «AI вроде работает» в измеримую инженерную дисциплину.
**Большинство про eval не думают — этим ты и выделяешься.**

### `app.py` — интерфейс (Streamlit)
Веб-чат. Показывает всё прозрачно: вопрос → «как я понял» → сворачиваемый SQL →
таблица → авто-график. Прозрачность (видимый SQL) — это тоже guardrail и признак
доверия: пользователь видит, откуда цифра.

### `report.py` — HTML-отчёт (артефакт)
Собирает из ответа бота **self-contained `.html`**: вопрос → интерпретация → SQL →
инлайновый **SVG-график** (нарисован руками, без библиотек) → таблица. Один файл,
ноль зависимостей, открывается двойным кликом даже без Python и интернета.
Запуск: `python report.py "топ-5 стран по обороту"`.

> Зачем: в агентной архитектуре агент не просто «возвращает строки», а отдаёт
> готовый **артефакт/борд**. Это мини-версия того самого «report», который агент
> кладёт пользователю.

### `mcp_server.py` — витрина для агента (MCP)
Экспонирует конвейер как **MCP-инструменты** (Model Context Protocol) — стандарт,
которым агент-оркестратор (Claude Desktop, Azure AI Foundry и т.п.) вызывает
внешние возможности. Инструменты:
- `list_metrics()` — словарь метрик (grounding: агент узнаёт, что доступно);
- `ask(question)` — полный NL→plan→SQL→данные с guardrails;
- `query_metric(...)` — прямой governed-вызов метрики без LLM.

> Это ровно «MCP-tool: query_metrics», описанный как главный путь агента к
> governed-семантике. Опциональный слой (`pip install "mcp[cli]"`) — ядро проекта
> работает и без него. Показывает, что MVP не «вещь в себе», а встраивается в
> агентную оркестрацию.

## 4. Словарь терминов (чтобы не плавать)

| Термин | Плоскими словами |
|---|---|
| **Semantic layer** | Словарь проверенных метрик между базой и пользователем/LLM |
| **Metric contract** | Метрика = формула + грейн + фильтры + разрешённые разрезы + владелец |
| **Structured output** | Заставляем LLM вернуть строгий JSON, а не свободный текст |
| **NL-to-SQL** | Перевод вопроса на естественном языке в SQL |
| **Guardrails** | Проверки, не дающие AI выполнить опасный/мусорный запрос |
| **Dry-run (EXPLAIN)** | Оценить запрос, не выполняя его |
| **Evaluation / eval** | Измерение точности AI на тестовом наборе |
| **Few-shot** | Примеры «вопрос→ответ» в промпте для повышения точности |
| **Fallback** | Резервный режим без LLM (матчинг по синонимам) |
| **Provider-agnostic** | Работает с любым LLM, нет привязки к вендору |
| **RAG (заложено на будущее)** | Когда метрик сотни — искать релевантные через embeddings, а не пихать все в промпт |

## 5. Как объяснять на защите (короткие тезисы)

- **Главное отличие:** «LLM не пишет SQL — она выбирает из семантического слоя,
  а SQL собирает детерминированный движок. Это убирает галлюцинации в джойнах и грейне.»
- **Про доверие:** «Многослойные guardrails + видимый SQL + "как я понял вопрос".
  Для регулируемого финтеха точность метрики = вопрос compliance, а не эстетики.»
- **Про измеримость:** «Есть eval-харнесс — меряю точность, ловлю регрессии при
  смене модели. Без этого AI-система неуправляема.»
- **Про архитектуру:** «Провайдер-агностично, работает без ключа на fallback.
  Semantic layer готов быть источником и для BI, и для LLM.»
- **Про честный scope:** «Это MVP. RAG-retrieval, MCP-деплой борда, RLS —
  осознанно оставил на следующий шаг, но заложил архитектурно.»

## 6. Как запустить

```bash
pip install -r requirements.txt
python generate_data.py            # создать базу (можно пропустить — создастся сама)
python pipeline.py "депозиты по странам"   # проверить в терминале (L1)
python pipeline.py "сколько у нас стран"    # L2: governed SQL-fallback
python eval.py                     # прогнать качество (L1 + L2)
python report.py "оборот по инструментам"   # сгенерировать HTML-отчёт
streamlit run app.py               # веб-чат
```
Без ключа — работает на fallback (L2 недоступен, честный отказ). С ключом
(в `.env`) — на настоящей LLM, доступны оба уровня.

### Деплой как «дата-продукт»
- **Локально** — команды выше. `broker.duckdb` создаётся автоматически при
  первом запуске (если файла нет), так что «свежий clone» поднимается без
  ручных шагов.
- **Живой URL** — деплой на **Streamlit Community Cloud** (бесплатно): связать
  GitHub-репозиторий → выбрать `app.py` → получить публичную ссылку. Ревьюер
  открывает URL без установки чего-либо. По умолчанию крутится на fallback
  (ключ не нужен). Ключ, если нужен, кладётся в Secrets Streamlit Cloud, а не
  в репозиторий.

## 7. Умный отказ и governance (`SemanticLayer.reject_message`)

Когда вопрос не сопоставился ни с метрикой (L1), ни с корректным SQL (L2),
система **не выдумывает**, а честно отказывает — но по-человечески: перечисляет,
что умеет, и даёт примеры. Это governance-принцип «лучше честное "не знаю",
чем уверенная галлюцинация» — критично для регулируемого финтеха.

Разница на примерах:
- «сколько депозитов по странам» → L1 (сертифицированная метрика);
- «сколько у нас стран» → L2 (ad-hoc SELECT под guardrails, помечен ⚠️);
- «какая погода в Лимассоле» → отказ с подсказкой (нет ни метрики, ни таблицы).
